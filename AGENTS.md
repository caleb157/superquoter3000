- Tasks link to at most one thing via association_type/association_id/association_label (inquiry_id/customer_id kept in sync for existing views; product_id deprecated) — new link kinds need no schema change.
- Recurring tasks are one living row: completing logs a done copy and rolls due_date forward (src/lib/task-recurrence.ts) — keeps the open list clean with history preserved.
- Odoo-triggered task sets come from task_automation_rules via the odoo-task-webhook function, authenticated by the admin-only token in task_automation_config — Odoo pushes events, HQ never polls.
- Master Analytics reads Odoo/LaborTrax actuals only from the latest `analytics_snapshots` row written by the `odoo-analytics-sync` function on manual Refresh; pipeline is computed live client-side in `src/lib/master-analytics.ts` — keeps the page instant and Odoo load on demand.
- HQ-originated task automations (inquiry created, customer set to Lead) fire from database triggers via run_hq_task_automation, sharing task_automation_rules with Odoo events — catches every insert path (UI, imports, MCP) without client code.
- App navigation is a single left slide-out menu; reference tables are grouped under an expandable "Directories" section — keeps the header uncluttered.
- Pipeline certainty = per-inquiry override, else booked 100% / cancelled-paused 0%, else the Settings default (global_settings.default_certainty_pct, cached via src/lib/projection-defaults.ts) — stage weighting retired so one knob drives all projections.
- Master Analytics projections are Parable Ventures-only: when another entity sells, PV revenue = FOB × (1 − selling retention) paid via inter-entity deposit/balance; missing projection FOB/man-hours fall back to the live costing engine (src/lib/pipeline-live.ts).
- Analytics opening cash comes from the sum of Odoo asset_cash accounts in the sync snapshot — no manual input.
- The inquiry Bulk Costing Editor (/inquiry/:id/audit) edits products/cbm_estimates/cogs_items directly and recomputes every derived number through computeProductCosting in memory — no separate math, so it can never disagree with the costing sheet.
- Analytics capacity (booked hours + available capacity) is a straight read of LaborTrax GET /api/public/capacity-forecast stored in the sync snapshot — so HQ matches LT's chart including manual Work Order overrides.
- Costing Intake (src/lib/costing-intake.ts) is the one spreadsheet format for bulk costing input, used by Import products (create) and the Bulk Editor (update by SKU, then name); it writes raw inputs only and lets the costing engine derive everything — so imports can never disagree with the costing sheet.
- The Costing Workspace (/inquiry/:id/costing) is the one place to cost an inquiry: it replaced the Pricing Grid, Target Grid and Bulk Costing Editor, whose routes now redirect to its views. It loads one in-memory bundle (src/lib/costing-workspace.ts), recomputes every number through computeProductCosting on each edit, writes through to the DB, and persists engine-derived values with persistResolvedCosting shortly after — so it can't disagree with the costing sheet.
- Costing Workspace sizes are separate W / D / H number columns (grouped under one header) and every grid cell carries data-grid/data-row/data-col, so keyboard navigation is a DOM lookup in costing-workspace/cells.tsx (spreadsheet model: arrows move, typing or F2 edits, Enter/Tab commit and move, block paste fills down and across) — no per-view key wiring.
- Contribution rate = (net profit + indirect overhead absorbed) ÷ FOB, with the indirect share carrying its cost of capital; computed in buildRows/totals (src/lib/costing-workspace.ts) from the engine's indirectOhPerUnit — bought-in items have no man-hours so trading work shows contribution = NPM, which makes trading and manufacturing orders comparable.
- Iron Weight Calculator (/tools/iron-weight) keeps all weight math in src/lib/iron-weight-core.ts (supplied, tested, formulas untouched); the working draft lives in localStorage and named builds in iron_builds keyed by free-text SKU + label (deliberately not linked to products), and the photo estimate (estimate-iron-parts) only drafts editable parts — the app always recomputes weights itself.
- Postponing a task (1 day / 1 week / 1 month, from the list row or the task card) counts from the later of today and the current due date (src/lib/task-postpone.ts), so an overdue task lands in the future; it saves immediately with Undo.
- Running inches = longest + shortest side (long side only for the "Wood Table" type, or a per-product running_inches_override); wood finishing labor is a ₹/running-inch budget (finishing_difficulty.rupees_per_ri × % wood) converted to man-hours at the average Finishing rate, packaging is 0.015 MH per running inch — all in autoLaborEstimate (costing-engine.ts), applied only to rows still flagged is_auto_estimated so hand-entered hours are kept.
- The inquiry clock (strip at the top of an inquiry) counts from the received date, or the creation time when logged that same day, to the first saved quote; amber from 3 days, red from 7, grey while not active — all in src/lib/inquiry-clock.ts, read from existing rows with no new tables.
- Quotes are generated in one click (Products and Assemblies tabs) through src/lib/quote-rough.ts — live engine prices, sorted by name, last-used Incoterm — and edited afterwards; there is no review dialog.
- A sent quote is never changed: the first save in Edit quote copies it to a new draft version (Q-…-v2, version/version_of on quote_snapshots, src/lib/quote-versions.ts), so the customer's copy stays exactly as sent.
- Samples are organised as sample requests (sample_requests, one per batch) with samples rows as lines (request_id); line status pending = requested, completed = received at our factory (completed_at), cancelled. The sample clock runs from the request date until every live line is received (src/lib/sample-requests.ts); product sample_stage is set by the existing samples trigger (open -> sampling, received -> sampled), so projections keep reading it. The old inquiry_received_rfs log was moved into requests and is no longer written.
- Analytics timing KPIs (Inquiry → quote, Samples → received) read the same clocks as the inquiry strips via src/lib/timing-kpis.ts: medians of clocks that stopped in the period, a 6-month trend and open ones listed in the drill-down — so the dashboard can't disagree with what each inquiry shows. The old RFQ-log pairing (pairRfqsToQuotes) is no longer used there.
